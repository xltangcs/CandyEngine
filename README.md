# CandyEngine

English | [中文](README_zh.md)

CandyEngine is a 2D game engine written in C++20 with a built-in editor, built on an ECS architecture (powered by [EnTT](https://github.com/skypjack/entt)). The current architecture is inspired by and built upon [The Cherno](https://github.com/TheCherno)'s [Hazel Engine](https://github.com/TheCherno/Hazel), while the design philosophy further leans toward Godot and Unreal Engine — engine and editor as one integrated system, scene-as-data, and ECS as a means rather than an end.

### Quick Start

This project uses `premake5.lua` as the single source of truth for the build. The `.sln` / `.vcxproj` files are generated by scripts and are gitignored.

```bash
# 1. Clone the repository (no --recursive needed — third-party deps are merged in via git subtree)
git clone https://github.com/xltangcs/CandyEngine.git
cd CandyEngine

# 2. Generate the Visual Studio solution (premake5 → .sln / .vcxproj)
.\Scripts\GenerateProjects.bat

# 3. Build with MSBuild (or open CandyEngine.sln in Visual Studio)
msbuild CandyEngine.sln /p:Configuration=Debug

# 4. Run the editor
.\bin\Debug-windows-x86_64\CandyEditor\CandyEditor.exe
```

> Third-party dependencies (GLFW, glm, yaml-cpp, ImGuizmo, box2d, imgui, pybind11, etc.) are merged directly into the repo via **git subtree**, so no submodule fetch is needed — you can generate the projects and build right away.

Build configuration macros: `Debug` → `CANDY_DEBUG`, `Release` → `CANDY_RELEASE`, `Dist` → `CANDY_DIST`.

### Done

| Module | Description |
|------|------|
| **Build System** | premake5 generates the project, supporting Debug / Release / Dist configurations |
| **Layer Stack** | Normal layers + overlays (ImGui is always an overlay), events propagate in LIFO reverse order |
| **ECS** | Based on EnTT; `Scene` holds an `entt::registry`, `Entity = entt::entity + Scene*` |
| **Rendering** | Layered RHI architecture (`RHIDevice` / `RHICommandBuffer` / `RHIFramebuffer`), D3D12 as the primary backend + OpenGL as the reference backend; `Renderer2D` batches quads / circles / lines / sprites through a single path; ImGui is decoupled from the render backend via the `ImGuiBackend` interface |
| **Physics** | Box2D integration: `Rigidbody2DComponent` (Static/Dynamic/Kinematic), `BoxCollider2DComponent`, `CircleCollider2DComponent`; runs only in Play / Simulate |
| **Native Scripting** | C++ `ScriptableEntity` base class + `NativeScriptComponent::Bind<T>()` |
| **Python Scripting** | pybind11 integrated, providing `candy.ScriptObject` (`on_construct` / `on_tick` / `on_destroy` lifecycle); the JumpGame sample is implemented purely in Python |
| **Editor** | Scene Hierarchy, Content Browser, Project Settings, Editor Settings |
| **3-State Scene Mode** | Edit (direct editing, no physics) / Play (deep-copied scene, physics + native scripts) / Simulate (deep copy, physics only, editor camera) |
| **Scene Serialization** | `.candy` files (yaml-cpp), human-readable, version-controllable, and mergeable |
| **Virtual File System** | VFS (`VFS://` protocol + Pak packaging) |
| **Audio** | miniaudio integration |
| **UI System** | `UITextBlockComponent` / `UIButtonComponent` and more |
| **Logging** | spdlog wrapper (`CANDY_CORE_*` / `CANDY_*`) |

**Sample Projects**
- **JumpGame**: a jump-and-dodge game demo implemented in pure Python scripts, located under `JumpGame/`.

### Future Plans

- **Scene Graph / Node Hierarchy**: introduce a Godot-like node hierarchy so Entities gain parent-child transform relationships.
- **Python Scripting Polish**: fully wire the pybind11 skeleton into the engine runtime, enabling hot-reload of Python logic in the editor.
- **Asset Pipeline**: implement a Godot/UE-style asset import & management system (Content Browser enhancements, `.import` flow).
- **Scene Inheritance & Instantiation**: let `.candy` scenes support inheritance and instantiation.
- **Frames in Flight**: eliminate the `WaitIdle` full-GPU stall at the end of `Renderer2D::Flush` — rotate the camera CB / vertex VB across frame slots (2~3 sets), and use fence barriers to confirm the GPU has consumed a slot before reusing it, letting CPU preparation of the next frame overlap with GPU rendering of the current one.
- **Dirty Tracking**: have the command buffer cache the current PSO / vertex buffer / texture / constant buffer bindings, skip redundant sets, and only issue GPU commands on real changes; this significantly cuts CPU submission overhead as draw calls grow (aligned with UE's `FRHICommandList` approach).
- **Render Backend Expansion**: re-enable the Vulkan backend (currently frozen; ported by mapping D3D12 ↔ Vulkan concepts); Metal is a longer-term consideration.
- **Visual Scripting**: a node-based, UE Blueprint-like scripting system.
- **SerializeRuntime**: complete runtime scene serialization.
